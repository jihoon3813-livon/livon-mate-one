## 검증 중 새로 드러난 것 (이전 문서의 확신 재점검)

### ① `?env=dev` 우회 — 04번 문서가 서술한 것보다 실제로 더 심각함

04번 문서 C-1은 "클라이언트가 SUPER_ADMIN처럼 보이는 UI를 그린다"는 선까지만 증명했다. 재검토 중 추가로 확인한 연결고리:

```
app.js:43222   localStorage.setItem('REBORN_ADMIN_SESSION_TOKEN', 'dev_session_' + Date.now());
convex/sync.js:14   if (args.sessionToken.startsWith("dev_session_")) { isAuthenticated = true; }
```

`bundleAll`(서버 측 Convex 함수)이 `dev_session_`로 시작하는 토큰이면 **서명·만료 검증 없이 무조건 인증된 것으로 처리**한다. 즉 `?env=dev`는 화면만 속이는 게 아니라 **Convex 서버 자체가 실제 고객 데이터를 내려준다.** 04번 문서 작성 시점엔 이 마지막 연결고리(app.js → sync.js:14)를 밟지 않고 "인증 우회"라고만 썼다 — 결론은 맞았지만 근거 사슬이 한 칸 빠져 있었다.

## 3. 서로 모순되는 분석 결과

- **회사 자체 문서 vs 코드 분석**: 개발중간보고서는 "원클릭 개인정보 마스킹으로 개인정보보호법 완벽 준수"라고 명시하지만, 04번 문서 C-6은 주민등록번호가 평문 저장·무인증 조회 가능하다고 결론냈다. 둘 다 사실이다 — **마스킹은 "화면 표시" 문제고 C-6은 "저장/전송" 문제**라서 모순이 아니라 서로 다른 층위인데, 이 구분을 어느 문서에서도 명시적으로 짚지 않았다. 새 개발자가 회사 보고서만 믿으면 "이미 컴플라이언스가 해결됐다"고 오해할 수 있다.
- 01번 문서는 RBAC를 "존재하는 기능"으로 서술(admins 테이블, 메뉴 권한)하는 반면 04번 H-1은 "RBAC가 서버에서 전혀 검증되지 않아 사실상 장식"이라고 결론낸다 — 모순이 아니라 심화 발견이지만, 06번 인수인계 문서를 서두만 읽는 사람은 "RBAC 있음"으로 오독할 수 있는 배치다.
- 03번 문서는 "Convex mutation = 트랜잭션 원자적"이라고 (Convex 공식 가이드라인을 인용해) 단언했는데, 04번 H-7(`resetSamsungCareLedger`)에서는 "함수가 끝까지 실행된 뒤 반환문에서 에러가 나면 이미 커밋된 삭제가 롤백되는지 확인 필요"라고 유보적으로 썼다. 두 서술이 나란히 있으면 "트랜잭션이 보장된다며 왜 부분실패가 걱정되냐"는 혼란을 줄 수 있다. Convex 런타임에서 함수 말미의 uncaught exception이 실제로 롤백을 유발하는지는 **결국 실행해봐야 아는 부분**(4장과 직결).

## 4. 실제 실행하지 않고는 확인할 수 없는 내용

- `server.js:1884`의 `os is not defined` — grep으로 `require('os')` 부재는 확인했지만, 실제로 해당 라우트를 호출했을 때 정말 `ReferenceError`가 나는지는 실행해야 확정.
- `resetSamsungCareLedger`의 반환문 `ReferenceError`가 실제로 앞선 `ctx.db.delete()` 커밋을 롤백시키는지 여부 — Convex 런타임의 실제 트랜잭션 커밋 타이밍은 문서 인용만으로 단정할 수 없고, 실제 실행 후 Convex 대시보드로 데이터가 지워졌는지 확인해야 한다.
- `?env=dev` + `dev_session_` 토큰 조합이 실제 배포된 Convex 프로덕션 인스턴스에서도 (개발용 인스턴스가 아니라) 똑같이 뚫리는지 — 코드상으론 동일하게 뚫리지만, **이 저장소의 `convex/sync.js`가 실제 배포된 함수 코드와 100% 동일하다는 전제 자체가 미검증**이다.
- `start_server.ps1`으로 켰을 때 정말로 CTI/CarePort/이메일 라우트가 404 나는지 — 코드 읽고 추론했을 뿐 실제로 켜서 요청을 보내보지 않았다.
- 인덱스 미사용 쿼리들이 "현재 규모에서 체감 지연 적음"이라 쓴 부분 — 실측 응답시간 측정 없이 순수 정성적으로 추정한 것이다.

## 6. 새 개발자가 잘못 이해할 가능성이 높은 부분

1. README "실행 방법"만 보고 `start_server.ps1`을 `node server.js`의 동등한 대안으로 여기고 로컬 테스트 → 팩스가 "성공"으로 뜨는데 실제로 안 나간 걸 못 알아챈다(05번 문서에서 지적했지만, README 자체는 여전히 고쳐지지 않은 상태).
2. 개발중간보고서를 읽고 "AWS 음성일지 파이프라인이 이미 돌고 있다"고 믿고 관련 기능 확장을 시도하다 코드에 아무것도 없어서 당황한다.
3. "개인정보 마스킹 기능 있음 = 개인정보 안전"으로 오해한다(3장 항목 참고).
4. `convex/applications.js`를 보고 "이게 진짜 API인가보다" 하고 여기에 새 로직을 얹었다가, 실제로는 `sync.js`가 쓰이고 `applications.js`는 죽은 코드라 아무 효과가 없음을 나중에 발견한다.
5. `admins` 테이블에 role/permission 필드가 있는 걸 보고 "서버가 권한을 검사하는구나"라고 짐작한다(실제로는 UI 표시용일 뿐).
6. `server.js`의 중복 라우트(`/api/samsung-drive/status`가 2곳) 중 뒷부분을 수정하고 "고쳤다"고 착각한다.
7. `.env.example`의 `CONVEX_URL`을 바꾸면 환경이 전환된다고 믿는다(실제로는 app.js 하드코딩이 우선한다).

## 8. 현재 분석에서 누락되었을 가능성이 높은 의존성

- **AWS SDK 관련 의존성 자체가 통째로 보이지 않는다** — 이게 정말 없는 건지, 이 스냅샷에서만 빠진 것인지 확인 필요(1장과 동일 맥락).
- `build_clean_dataset.js`/`migrate_audited_to_cloud.js`가 참조하는 `node_modules/.xlsx-TKVotygl`은 **이 checkout에 실제로 존재하지 않는다**(확인 결과: `node_modules`에는 `convex`뿐). 즉 이 두 스크립트는 **지금 이 상태로는 실행 시도하면 즉시 `MODULE_NOT_FOUND`로 죽는다** — 03/05번 문서에서 "수동 실행 가능한 스크립트"처럼 서술했는데, 정확히는 "특정 시점에 임시로 설치된 패키지에 의존하는, 현재는 실행 불가능한 스크립트"로 정정이 필요하다.
- SMS 발송 대행사 SDK(survey-service.js가 SMS를 실제로 어떤 업체로 보내는지) — 관련 라이브러리 require가 보이지 않는데, 이것이 "SMS 발송 기능이 미완성"인지 "누락된 파일이 있는지" 구분되지 않는다.
- Barobill/CarePort 등이 내부적으로 특정 인증서 파일(`.pfx`, `.pem` 등)을 요구할 가능성 — 코드상 파일 경로 참조는 찾지 못했지만 SOAP/FTP 연동 특성상 존재할 수 있어 배제할 수 없다.

## 9. 장애 발생 시 원인 추적이 특히 어려운 부분

1. **이중 저장소 불일치**: Convex와 `hub_apps_real.json`이 갈라진 뒤에는, 로그가 콘솔에만 남고 "언제부터 갈라졌는지" 타임스탬프 비교 수단이 코드에 없다 — 추적하려면 두 저장소를 수동으로 diff 떠야 한다.
2. **`syncToConvex`의 전역 실패 삼킴 패턴**: 실패가 `console.warn` 한 줄로만 남고 사용자 화면엔 아무 표시가 없어서, "왜 이 데이터만 저장이 안 됐지"를 재현하려면 그 순간의 브라우저 콘솔 로그가 남아있어야 하는데 보통 이미 닫혀서 사라진다.
3. **`/api/fax/status`의 오류 은폐**(항상 200 + 가짜 정상값) — 이 엔드포인트를 신뢰해서 만든 모니터링/알림이 있다면, 실제 장애 중에도 "정상"으로 보여서 장애 감지 자체가 늦어진다.
4. **GoodARS HTML 스크레이핑**: 응답 형식이 바뀌면 예외 없이 빈 배열/일부만 파싱되는 방식이라(여러 곳 `catch(err){}` 무음 패턴), "콜 데이터가 왜 일부만 들어왔는지"가 코드 레벨에서 전혀 로깅되지 않는다.
5. **`resetSamsungCareLedger`류 부분실패**: 에러 응답을 받고도 실제로는 데이터가 이미 바뀐 상태 — "실패했다고 들었는데 왜 데이터가 사라졌지"라는 가장 혼란스러운 유형의 장애다.
6. **브라우저별 낙관적 캐시**: 사용자 A와 B가 서로 다른 `localStorage` 캐시 시점을 보고 있어서, "내 화면엔 있는데 쟤 화면엔 없다"는 보고가 실제 버그인지 단순 캐시 시차인지 구분되지 않는다.
