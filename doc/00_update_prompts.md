# 00. 문서 갱신 프롬프트 모음 (Update Prompts)

> 이 문서는 `doc/01_Architecture_Discovery.md` ~ `doc/07_self_review.md` 7개 인수인계 문서를, **코드가 변경된 이후 다시 최신 상태로 업데이트**시키기 위한 재사용 가능한 프롬프트 모음이다. 새 담당자든 AI 에이전트든, 코드가 바뀔 때마다 이 문서에 있는 프롬프트를 그대로(또는 괄호 안을 채워서) 복사해 실행하면 된다.
>
> **왜 매번 처음부터 다시 만들지 않는가**: 01~07번 문서는 특정 커밋(`1278873`, 2026-09-28) 시점 기준으로 전체 코드베이스를 정밀 분석해 작성됐다. 코드가 바뀔 때마다 전체를 처음부터 다시 쓰면 시간이 오래 걸리고, 바뀌지 않은 부분까지 재검증하느라 비효율적이다. 아래 프롬프트들은 **"이전 문서 + 변경분 diff"를 입력으로 받아, 영향받은 부분만 갱신**하도록 설계되어 있다.

## 0. 공통 원칙 (모든 갱신 작업에 적용)

모든 개별 프롬프트는 다음 원칙을 항상 포함한다. 프롬프트를 직접 수정해서 쓰더라도 이 원칙은 지워선 안 된다.

- 실제 소스코드에 존재하는 내용과 추론한 내용을 구분한다. 추론은 문장 끝에 **(추론)** 또는 **(추정)** 으로 표기한다.
- 코드에서 확인할 수 없는 내용은 추측하지 않고 **"확인 필요"** 로 표시한다.
- 모든 서술에는 `파일:라인` 근거를 남긴다.
- 기존 문서의 결론을 무조건 유지하지 않는다 — 코드가 바뀌어 더 이상 사실이 아니게 된 서술은 반드시 수정하거나 삭제한다.
- 문서 최상단의 `> **분석 기준**: git \`main\` 브랜치, 커밋 \`<커밋해시>\` (분석일 <YYYY-MM-DD>)` 줄을 새 커밋해시/날짜로 갱신한다.
- 문서 최하단(또는 상단 분석기준 바로 아래)에 **변경 이력**을 한 줄 추가한다. 형식:
  `- 2026-XX-XX (커밋 <이전해시>→<신규해시>): <무엇이 왜 바뀌었는지 한 줄 요약>`
- 이번 갱신에서 **변경되지 않은 섹션은 그대로 둔다.** 전체를 재작성하지 말고, 실제로 영향받은 절/문장만 고친다.

## 1단계 — 변경 범위 파악 (모든 갱신 작업 전 반드시 먼저 실행)

## 3단계 — 전체 일괄 갱신 (한 번에 다 돌리고 싶을 때)

```
Livon Care ERP 프로젝트의 코드가 doc/01~07 작성 시점(커밋 <이전 커밋 해시>) 이후 변경되었다. doc/00_update_prompts.md에 정의된 절차대로:

1. `git log <이전 커밋 해시>..HEAD --stat`와 `git diff <이전 커밋 해시>..HEAD`로 변경 범위를 파악하고, doc/00_update_prompts.md의 "1단계" 대응표에 따라 영향받는 문서를 판단하라.
2. 영향받는 문서에 한해, doc/00_update_prompts.md의 "2단계"에 있는 해당 문서용 프롬프트를 순서대로(01→02→03→04→05→06→07) 실행하라. 06번과 07번은 반드시 다른 문서들이 먼저 갱신된 뒤에 실행하라(종합/검증 문서이므로).
3. 각 문서 상단의 "분석 기준" 줄을 새 커밋 해시와 오늘 날짜로 갱신하고, 변경 이력 한 줄을 추가하라.
4. 영향받지 않는다고 판단한 문서는 건드리지 말고, 어떤 문서를 왜 건드리지 않았는지 최종 보고에 명시하라.
5. 작업 완료 후, 이번에 새로 발견된 사실이 기존 문서 간 모순을 만들지 않는지(예: 04번에서 위험으로 지적한 게 06번엔 여전히 안전한 것처럼 남아있는지) 간단히 교차 점검하라.
```

## 사용 팁

- 커밋 해시는 각 문서 상단의 `> **분석 기준**: git \`main\` 브랜치, 커밋 \`...\`` 줄에서 가져오면 된다. 문서마다 마지막 갱신 시점이 다를 수 있으므로, 갱신 전 01~07 전체의 "분석 기준" 줄을 먼저 확인해 가장 오래된 커밋을 기준으로 diff를 뜨는 것을 권장한다.
- 변경 규모가 작을 때(예: 파일 1~2개, 함수 몇 개 수정)는 굳이 1단계 대응표를 다 훑지 말고, "이 커밋이 `api/fax/send.js`만 건드렸다 → doc/01 7장, doc/02 시나리오4, doc/04 관련 항목만 확인" 식으로 직접 판단해도 된다.
- 변경 규모가 클 때(대규모 리팩터링, 신규 기능 다수 추가)는 처음 01~07을 만들 때와 마찬가지로 전체 재조사에 가까운 작업이 될 수 있다 — 이 경우 원본 대화(01번 문서 생성 시점)의 지시사항을 그대로 재사용해도 무방하다.
