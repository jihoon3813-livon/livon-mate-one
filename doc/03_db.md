## 0. 요약 — 이 시스템은 "단일 DB"가 아니다

코드 전체를 조사한 결과, 이 시스템은 하나의 정식 데이터베이스가 아니라 **4개의 서로 다른 저장소가 역할을 나누어 공존**하는 구조다. 정식 RDBMS(MySQL/PostgreSQL 등)나 Redis, MongoDB는 코드 어디에서도 발견되지 않았다.

| 저장소 | 실체 | 주 사용처 | 근거 |
|---|---|---|---|
| **Convex** | 클라우드 BaaS 문서 DB (`v.any()` 스키마) | 인증 세션, 핵심 엔티티의 원격 미러 | convex/schema.js, package.json:11-13 |
| **로컬 JSON 파일** | `hub_apps_real.json` 등, Node `fs`로 직접 R/W | 신청/배정/청구/지급/간병인/센터/손사 데이터의 사실상 1차 저장소 | server.js:802-1038 |
| **브라우저 `localStorage`** | 키-값 캐시 | UI 상태, 세션 토큰, 각 엔티티의 오프라인 캐시 | app.js 333회 참조 (01번 문서 5.3) |
| **브라우저 `IndexedDB`(`LivonDB`)** | 커스텀 래퍼 | 10만 건 이상 규모의 삼성화재 사전명단 등 대용량 로컬 데이터 | app.js:4183 |

이하 항목은 요청된 19개 항목을 위 4개 저장소 전반에 걸쳐 다루되, **정식 스키마·인덱스·트랜잭션 개념이 실질적으로 존재하는 곳은 Convex뿐**이므로 4~19번 항목은 Convex를 중심으로 서술하고, 로컬 JSON 파일의 "테이블"(최상위 배열)도 동등하게 취급하여 병기한다.

## 1. 사용하는 DB 종류

- **Convex** (`^1.45.0`, package.json:11-13) — SQL이 아닌 문서(document) 지향 BaaS. 자체 쿼리 빌더(`ctx.db.query(...)`)를 제공하며 내부 스토리지 엔진은 Convex 플랫폼이 관리(비공개, **확인 필요**: 내부적으로 어떤 스토리지를 쓰는지는 이 저장소 코드에서 알 수 없음).
- **로컬 JSON 파일** — 정식 DB가 아니라 Node `fs.readFileSync`/`writeFileSync`로 직접 읽고 쓰는 평문 파일. 대표적으로 `hub_apps_real.json`(applications/assignments/claims/payouts/caregivers/centers/adjusters 7개 배열 보유, 실측 1,489,657 bytes), `call_report_*.json`, `call_annotations.json`, `member_phone_map.json`, 런타임 생성 파일(`cti_config.json`, `email_config.json`, `fax_config.json`, `survey_data.json`, `samsung_drive_*.json` — 저장소에는 아직 존재하지 않으며 최초 실행/저장 시점에 생성되는 것으로 확인됨, 직접 파일시스템 조회로 검증).
- **브라우저 `localStorage`/`sessionStorage`** — 세션 토큰, 각 엔티티 캐시(`LIVON_CACHED_APPS` 등), UI 상태.
- **브라우저 `IndexedDB`** — `LivonDB`(app.js:4183)라는 커스텀 래퍼로 구현, "100,000+ Records without Quota Limits" 주석(app.js:4181) 근거로 대용량 데이터 전용.
- **RDBMS/Redis/MongoDB 등**: 코드베이스 전체에서 **미발견**.

## 2. Connection 설정

Convex는 전통적인 "커넥션"(TCP 소켓, 커넥션 풀) 개념이 없고, **매 호출이 독립적인 HTTP POST 요청**이다.

- 서버 함수(`convex/*.js`) 자체는 연결 설정 코드를 갖지 않는다 — Convex 배포 시 플랫폼이 알아서 라우팅.
- 프런트엔드는 공식 SDK(`ConvexHttpClient`)를 쓰지 않고, **자체 fetch 래퍼**로 직접 REST 엔드포인트를 호출한다:
  - `syncToConvex(path, args)` → `fetch(\`${CONVEX_URL}/api/mutation\`, {...})` — app.js:1107-1121
  - `queryConvex(path, args)` → `fetch(\`${CONVEX_URL}/api/query\`, {...})`, 10초 `AbortController` 타임아웃 — app.js:1123-1141
  - `CONVEX_URL`은 환경변수가 아니라 **소스에 하드코딩된 두 URL 중 하나**를 호스트/URL파라미터/localStorage 휴리스틱으로 선택: dev `https://rapid-raccoon-895.convex.cloud`(app.js:1080), prod `https://gallant-weasel-360.convex.cloud`(app.js:1081)
  - `.env.example`에는 `CONVEX_URL` 환경변수가 문서화되어 있으나(.env.example:7) **실제 프런트엔드 코드는 이를 읽지 않는다** — 문서와 구현의 불일치(01번 문서 8장과 동일 이슈)
- 로컬 JSON 파일은 "연결"이 아니라 매 요청마다 `fs.readFileSync`/`writeFileSync`로 직접 접근(예: server.js:918-988). server.js:200-230에 mtime 기반 인메모리 캐시가 있어 반복 읽기를 줄이는 정도의 최적화만 존재.
- 커넥션 풀, 재시도 정책, 헬스체크 등 정식 DB 클라이언트에서 기대되는 설정은 **미발견**.

## 3. ORM / Query Builder / Raw SQL 여부

- **Raw SQL: 없음** — SQL 데이터베이스 자체가 사용되지 않으므로 해당 없음.
- **ORM: 없음** — Prisma/TypeORM/Sequelize 등 미사용.
- **Query Builder**: Convex 자체 내장 쿼리 빌더만 사용됨 — `ctx.db.query("table").filter(...)`, `.withIndex(...)`, `.order(...)`, `.collect()`, `.take(n)`, `.paginate(...)` (convex/sync.js 전역).
  - `.filter((q) => q.eq(q.field("id"), value))` 패턴이 **36회**, `.withIndex(...)` 패턴이 **8회** 사용됨(convex/sync.js 실측 grep 카운트) — 즉 인덱스 활용 쿼리보다 **전체 스캔 후 필터링하는 쿼리가 4.5배 더 많다** (17-19장에서 상세).
  - `.collect()`(전체 결과 수집) 호출이 sync.js 내 **66회** — Convex 자체 가이드라인(`convex/_generated/ai/guidelines.md:333`)이 "큰 테이블에 `.collect().length`로 카운트하지 말라"고 명시할 정도로 대규모 컬렉션에서 지양되는 패턴이나, 이 프로젝트는 거의 모든 목록 조회·삭제 로직에서 `.collect()`로 테이블 전체를 메모리에 적재한다.
  - Convex는 쿼리 결과에 대한 `.delete()` 벌크 연산을 지원하지 않아(가이드라인 파일 336행 "Convex queries do NOT support `.delete()`"), 모든 삭제가 "조회 → 루프 순회 → 개별 `ctx.db.delete()`" 형태로 구현되어 있다 — 이는 Convex의 제약에 따른 **불가피한 패턴**이지 코드 결함이 아니다(단, 대상 건수가 많을 때의 성능 영향은 19장에서 별도 논의).
- 로컬 JSON 파일은 쿼리 개념 없이 `JSON.parse()` 후 JS 배열 메서드(`find`/`filter`/`map`)로 메모리 내에서 직접 조작(server.js 다수, app.js 다수).

## 7. PK / FK

Convex 문서는 시스템 내부적으로 항상 `_id`(Convex 자동 생성 Document ID)를 1차 키로 갖는다 — 이것이 **실질적인 PK**다(모든 `ctx.db.patch(existing._id, ...)`/`ctx.db.delete(x._id)` 호출이 이를 근거로 동작, sync.js 전역).

이와 별개로, 애플리케이션 코드는 **자체 발급하는 비즈니스 ID 문자열 필드 `id`를 논리적 PK처럼 사용**한다 (예: `applications.id`(형식 `C0001`류), `claims.id`, `payouts.id` 등). 이 `id` 필드에는 **스키마 레벨의 유일성 제약(unique constraint)이 없다** — `v.any()` 스키마이므로 Convex가 중복을 막아주지 않으며, 중복 방지는 오직 각 upsert 함수의 "조회 후 있으면 patch, 없으면 insert" 로직에 전적으로 의존한다(예: sync.js:125-135). 두 클라이언트가 동시에 같은 `id`로 최초 저장을 시도하면 **중복 레코드가 생성될 수 있는 구조적 위험**이 있다(11장 동시성 제어 참조).

**FK(외래키)**: Convex `v.any()` 스키마에는 FK 제약 자체가 존재하지 않는다. 다만 **코드 레벨에서 관례적으로 사용되는 논리적 FK**가 확인된다:

| 자식 필드 | 부모 테이블.필드 | 실제 코드 확인 여부 |
|---|---|---|
| `assignments.applyId` | `applications.id` | **실제 코드 확인** — `deleteApplication`이 이 필드로 cascade 삭제(sync.js:154-158) |
| `claims.applyId` | `applications.id` | **실제 코드 확인** — 동일(sync.js:160-164) |
| `payouts.applyId` | `applications.id` | **실제 코드 확인** — 동일(sync.js:166-170) |
| `caregivers.name` ↔ `assignments.caregiverName`/`payouts.caregiverName` | 문자열 매칭 | **추론** — 별도 ID 연결이 아닌 이름 문자열 매칭으로 연결되는 것으로 보임(01/02번 문서에서 확인된 `matchCenterSearch`류 패턴과 동일 계열, 확인 필요: 정확한 매칭 함수 위치) |
| `adjusters.name` ↔ `applications.adjusterName` | 문자열 매칭 | **추론**, 동일 사유 |
| `samsungSheets.patientId` ↔ `samsungEligible.patientId` | 느슨한 문자열 매칭 | **추론** — 둘 다 `patientId` 필드를 갖지만 이를 조인해 사용하는 쿼리 로직은 sync.js 내에서 **미발견** |
| `adminSessions.adminId` ↔ `admins.id` | 참조는 되나 정합성 미보장 | **실제 코드 확인** — `verifyAdminSession`이 `session.adminId`로 `admins`를 재조회(sync.js:1128-1131)하지만, `admins` 삭제 시 `adminSessions`를 정리하는 코드는 **없음**(20장 삭제 영향 분석 참조) |

## 8. 인덱스

Convex 인덱스가 실제로 정의된 곳은 4장의 표와 같이 **8개 테이블, 총 13개 인덱스**뿐이며, 나머지 15개 테이블은 인덱스가 전혀 없다(convex/schema.js:4-93).

**더 심각한 문제**: 인덱스가 정의된 테이블조차 코드에서 **인덱스를 쓰지 않고 `.filter()` 전체 스캔으로 조회하는 경우가 다수** 확인된다.

| 테이블 | 정의된 인덱스 | 실제 사용 여부 |
|---|---|---|
| `admins` | (인덱스 없음) | `loginAdmin`(sync.js:1052), `getAdmins`(sync.js:1039), `saveAdmin`(sync.js:1178), `saveAdminsChunk`(sync.js:1206) 모두 `.collect()` 후 JS `find()`로 **전체 스캔** |
| `adminSessions` | `by_token`, `by_adminId` | `verifyAdminSession`(sync.js:1117)·`logoutAdmin`(sync.js:1160)은 `by_token` 인덱스를 **올바르게 사용**. 그러나 `by_adminId` 인덱스는 **schema.js:65에 정의만 되어 있을 뿐, 이를 사용하는 쿼리가 sync.js 어디에도 없음** — 죽은 인덱스 |
| `caregivers` | `by_name`, `by_cg_id` | `saveCaregiver`/`saveCaregiversChunk`는 인덱스 사용(sync.js:1400-1409, 1436-1445). 그러나 `deleteCaregiver`(sync.js:1466-1469)는 `.filter()` 전체 스캔 사용 — **동일 테이블 내에서도 일관성 없음** |
| `samsungEligible` | `by_patientId`, `by_lead_id`, `by_policyNumber` | `saveSamsungEligible`(sync.js:377-383), `deleteSamsungEligible`(sync.js:448-454) 모두 `.filter()` 전체 스캔 사용 — **정의된 3개 인덱스 중 어느 것도 실제로 사용되지 않음** |
| `systemSettings` | `by_key` | `saveSystemSetting`(sync.js:1561)은 인덱스 사용. `resetSamsungCareLedger`(sync.js:1366-1369)는 `.filter()` 전체 스캔 사용 |
| `applications`/`assignments`/`claims`/`payouts`/`faxRecords`/`formConfigs`/`adjusters`/`partners`/`careLogs`/`samsungSheets`/`samsungAddressBook` | 없음 | 모든 조회가 `.filter()` 전체 스캔 또는 `.collect()` 전체 로드 |

인덱스가 없는 테이블은 애초에 인덱스를 쓸 수 없으므로, `applications`처럼 가장 핵심적인 테이블에서조차 `id` 필드로 단건 조회할 때마다(예: `saveApplication`, sync.js:125-128) **매번 테이블 전체를 스캔**한다. 향후 데이터가 수천~수만 건 규모로 늘어나면 쓰기 지연이 선형적으로 증가할 구조다.

## 10. Transaction 경계

- Convex는 플랫폼 차원에서 **하나의 query/mutation 함수 실행 전체를 하나의 트랜잭션으로 취급**한다 — 이는 이 저장소에 함께 포함된 Convex 공식 가이드라인 문서에 명시되어 있다: *"Queries and mutations are transactions, so splitting logic up into multiple calls introduces the risk of race conditions."* (convex/_generated/ai/guidelines.md:98). 즉 `deleteApplication`(sync.js:140-174)처럼 하나의 mutation 안에서 4개 테이블을 순회 삭제하는 로직은 **Convex 플랫폼이 원자성을 보장**한다(추론이 아닌 Convex 자체 문서 근거).
- 그러나 **애플리케이션 레벨에서는 이 경계가 자주 깨진다.** 다음은 모두 서로 다른 트랜잭션(별개의 HTTP 요청)으로 분리되어 있어, 중간에 실패하면 데이터가 불일치 상태로 남는다:
  - 시나리오 2(신규 접수): `POST /api/hub/create-application`(로컬 파일 기록)과 `syncToConvex('sync:saveApplication')`(Convex 기록)이 **서로 독립적인 두 호출** — app.js:39730, 39746
  - 시나리오 10(전체 초기화): `syncToConvex('sync:resetAndPurgeLaunchData')`와 `fetch('/api/admin/reset-local-data')`가 **서로 독립적인 두 호출** — app.js:33526, 33534
  - 정산 세트 생성 시 `saveClaim`과 `saveApplication`을 **연달아 별도 호출**(예: app.js:21188-21189) — 둘 사이에 원자성 없음
- 결론: **단일 테이블 내 cascade 삭제는 원자적이나, 서로 다른 저장소(Convex ↔ 로컬 JSON) 간, 또는 서로 다른 mutation 호출 간에는 트랜잭션 경계가 전혀 없다.**

## 11. 동시성 제어

- **낙관적 잠금(optimistic locking) 미구현**: 모든 upsert가 "조회 → 있으면 patch" 패턴이며, 버전 필드(`_version`, `updatedAt` 비교 등)를 확인한 후 patch하는 코드는 **미발견**. 즉 두 사용자가 동시에 같은 레코드를 수정하면 **나중에 도착한 요청이 먼저 것을 덮어쓴다**(Last-Write-Wins, 코드 구조로부터의 추론이나 명시적 버전 체크 부재는 실제 코드 확인 사항).
- **비관적 잠금(pessimistic lock) 미구현**: Convex/로컬 파일 어디에도 명시적 락 획득/해제 코드 없음.
- **로컬 JSON 파일 쓰기 경합**: `server.js`의 여러 라우트가 동일 파일(`hub_apps_real.json`, `call_report_*.json`)에 `fs.writeFileSync`를 직접 호출하며(server.js:918-988, 1111-1132 등), 파일 락(`flock` 등)이나 원자적 쓰기(임시파일→rename) 패턴이 **미발견** — 동시 요청 시 한쪽의 쓰기가 다른 쪽에 덮어써질 위험이 구조적으로 존재한다.
- **Convex 문서 ID 신규 생성 시 중복 방지 미보장**: 7장에서 서술한 대로, 비즈니스 `id` 필드의 유일성은 upsert 로직에만 의존하므로 동시 요청 시 중복 insert 가능성이 있다(추론, 원인은 실제 코드 확인).

## 12. Lock 사용 여부

- **DB 레벨 Lock**: Convex는 자체 트랜잭션 내에서 내부적으로 충돌을 관리하는 것으로 알려져 있으나(플랫폼 동작, **확인 필요**: 이 저장소 코드로는 내부 구현 검증 불가), 애플리케이션 코드가 명시적으로 락을 요청/해제하는 API(`SELECT ... FOR UPDATE` 상당 기능)를 호출하는 부분은 **미발견**.
- **파일 Lock**: 로컬 JSON 파일 R/W 경로 전체에서 `fs.flock`, `proper-lockfile` 등 락 라이브러리 사용 **미발견**.
- **애플리케이션 레벨 뮤텍스/세마포어**: 미발견.
- 결론: 이 시스템 전체에서 확인되는 유일한 "동시성 보호"는 Convex 플랫폼이 단일 mutation 실행 단위에 대해 제공하는 트랜잭션 격리뿐이다.

## 13. Migration 방식

- **버전 관리되는 스키마 마이그레이션 도구/파일이 존재하지 않는다.** `convex/schema.js`를 직접 수정한 뒤 `npx convex dev`/`deploy`로 배포하는 것이 유일한 스키마 변경 경로로 추정된다(추론, package.json:9 `"convex": "node node_modules/convex/bin/main.js dev"` 근거). Convex 자체가 `v.any()` 스키마라 필드 추가/변경에 별도 마이그레이션이 필요 없는 구조이기도 하다.
- **데이터 마이그레이션(이관)은 수동 스크립트로 수행**된 것으로 확인된다:
  - `build_clean_dataset.js` — 특정 엑셀 파일 1개를 파싱해 `hub_apps_real.json`을 생성하는 1회성 스크립트(함수 래핑 없이 최상위에서 즉시 실행, `require.main` 가드 없음)
  - `migrate_audited_to_cloud.js` — 동일 엑셀을 파싱 후 **로컬 파일 저장 + Convex 청크 업로드**까지 수행하는 1회성 이관 스크립트, `fetchWithRetry`로 최대 5회 재시도(선형 백오프)와 50건 단위 청크 업로드(300ms 지연)를 구현(migrate_audited_to_cloud.js:450-486)
  - 두 스크립트 모두 `package.json` scripts, `server.js`, `index.html`, `app.js` 어디에서도 호출되지 않는 **완전 수동 실행 전용**(01번 문서 부록 확인 결과와 동일)
- **정식 down-migration(롤백) 스크립트는 미발견**.

## 14. 초기 데이터 생성 방식

- `convex/seed.js`가 범용 시드 mutation 2개를 제공: `seedBatch(table, items)`(seed.js:5, 임의 테이블명 문자열을 받아 그대로 insert — 스키마 검증 없이 존재하지 않는 테이블명을 넘기면 Convex가 런타임에 에러를 던질 것으로 추정, **확인 필요**), `clearTable(table)`(seed.js:23, **500건 상한 `.take(500)`으로 그 이상은 부분 삭제만 수행**하고 별도 경고 없이 종료 — 대량 테이블 초기화 시 불완전 삭제 위험).
- 실질적인 초기 데이터는 위 13장의 두 ETL 스크립트(`build_clean_dataset.js`, `migrate_audited_to_cloud.js`)를 통해 엑셀 관리대장으로부터 1회성으로 적재된 것으로 확인됨.
- 운영 중 "전산 런칭" 시나리오(02번 문서 시나리오 10과 연계)에서는 `resetAndPurgeLaunchData`(sync.js:1260)로 기존 데이터를 지운 뒤, 프런트엔드의 엑셀 업로드 파서(app.js:46531-48642 "실데이터 런칭 엔진")가 `saveApplicationsChunk` 등으로 재적재하는 흐름이 반복적인 "초기화" 수단으로 사용되는 것으로 보인다(추론, 02번 문서 참조).

## 15. Soft Delete 여부

- **Soft Delete 미구현.** 스키마가 `v.any()`이므로 이론적으로는 `isDeleted`/`deletedAt` 같은 필드를 추가하는 것이 가능하나, `convex/sync.js` 전체에서 그런 필드를 설정/필터링하는 코드는 **미발견**. 모든 삭제 함수(`deleteApplication`, `deleteClaim`, `deletePayout`, `deleteFaxRecord`, `deleteSamsungEligible`, `deleteCaregiver`, `deleteAdminDoc` 등)가 예외 없이 `ctx.db.delete(x._id)`로 **완전 삭제(hard delete)**를 수행한다.
- 유사 개념으로 `isRealLaunchData` 플래그(applications 등)가 존재하나, 이는 "삭제 표시"가 아니라 **"목업/테스트 데이터 여부"를 구분해 `purgeMockData`(sync.js:884)가 선택적으로 진짜 삭제할 대상을 고르는 용도**다 — Soft Delete와는 목적이 다르다.
- 관리자 계정(`status: "비활성"`)은 "삭제 대신 비활성화"라는 유사 개념이 로그인 로직(sync.js:1059-1061)에 존재하나, 이 역시 계정 도메인에 한정되며 범용 Soft Delete 패턴은 아니다.

## 16. Audit 데이터 처리

- **DB 레벨의 공식 audit 테이블/로그는 존재하지 않는다.** `convex/schema.js` 23개 테이블 중 "감사"/"이력" 목적의 테이블은 없다.
- 유일하게 감사로그를 표방하는 것은 `system-audit-log.js`이며, 01번 문서 5.4에서 이미 확인된 바와 같이 **순수 브라우저 `localStorage` 기반**(`window.gSystemAuditLogs`, `LIVON_SYSTEM_AUDIT_LOGS` 키)으로, 서버/DB에 영속되지 않고 사용자가 `clearAuditLogs()`(system-audit-log.js:809-833)로 스스로 지울 수 있다. 즉 **DB 관점에서는 감사 데이터가 전혀 보존되지 않는다.**
- 각 upsert 함수가 `updatedAt`(문자열, ISO 또는 커스텀 포맷)을 갱신하는 정도가 유일한 "변경 시각 추적"이며, **누가(actor) 변경했는지, 변경 전 값이 무엇이었는지는 DB에 남지 않는다** — `system-audit-log.js`의 `changes: {before, after}` 구조(예: app.js:39707-39714)가 이 역할을 대신하려 하지만 이 역시 클라이언트 로컬 저장일 뿐이다.
- Convex 문서는 `_creationTime`이라는 플랫폼 기본 필드를 암묵적으로 갖지만(모든 Convex 문서 공통, 프레임워크 기본 동작), 이를 조회해 "생성 시각"으로 활용하는 애플리케이션 코드는 **미발견**(대신 `importedAt`, `createdAt` 등 자체 문자열 필드를 별도로 관리).

## 17. N+1 가능성이 있는 코드

가장 명확한 N+1 패턴은 **청크(chunk) 저장 mutation들의 루프 내 개별 쿼리**다.

- **`saveApplicationsChunk`**(sync.js:734-782): `args.apps` 배열(엑셀에서 파싱된 수백 건)을 순회하며, 각 항목마다 `ctx.db.query("applications").filter((q) => q.eq(q.field("id"), doc.id)).first()`를 **개별 실행**(sync.js:771-774). `applications`에는 인덱스가 없으므로 이 필터는 매번 **테이블 전체 스캔**이다. N건을 저장하면 O(N × 테이블크기)의 스캔이 발생하는 전형적 N+1(정확히는 "N번의 전체 스캔") 패턴.
- 동일 패턴이 **`saveAssignmentsChunk`**(sync.js:810), **`saveClaimsChunk`**(sync.js:843), **`savePayoutsChunk`**(sync.js:876), **`saveCaregiversChunk`**(sync.js:1436-1445, 다만 이쪽은 인덱스 사용), **`savePartnersChunk`**(sync.js:1491-1500), **`saveAdjustersChunk`**(sync.js:1527-1536)에도 반복된다.
- **`saveAdmin`/`saveAdminsChunk`**(sync.js:1178, 1206)는 매 호출마다 `admins` 테이블 전체를 `.collect()`한 뒤 JS `find()`로 순회 — 테이블 자체는 작을 것으로 예상되어(관리자 수는 적음, 추론) 실질적 위험은 낮으나 동일한 안티패턴.
- **`resetAndPurgeLaunchData`/`purgeMockData`/`purgeStale*`**(sync.js:884-1033, 1260-1346) 계열은 전체 테이블을 `.collect()`한 뒤 **한 건씩 `await ctx.db.delete()`를 순차 실행** — Convex 제약상(13장) 불가피한 구조이지만, 수천 건 삭제 시 수천 번의 순차 await가 발생해 응답 지연이 커질 수 있다.
- **브라우저 측 유사 패턴**: `cti-client.js`의 `fetchCtiLogsByDateRange()`(cti-client.js:470-775)가 신규/당일 통화 최대 30건에 대해 **건별로 상세조회 HTTP 요청**을 보내는 구조(cti-client.js:743-756, 15건씩 배치 처리로 일부 완화)— DB N+1은 아니지만 외부 API에 대한 동일한 클래스의 문제.

## 18. 위험한 Query

1. **`/api/admin/reset-local-data` + `sync:resetAndPurgeLaunchData`**(server.js:916-937, sync.js:1260-1346): 인증 없이 호출 가능하며, 관리자 계정을 제외한 **모든 업무 데이터를 즉시 영구 삭제**한다. 백업/확인 절차가 서버 측에는 전혀 없다(02번 문서 시나리오 10과 동일 이슈, DB 관점에서 재확인).
2. **`purgeStaleApplicationsNotInList`**(sync.js:970-988): 클라이언트가 넘긴 `validIds` 배열에 없는 모든 `applications`를 삭제한다. **연관된 `assignments`/`claims`/`payouts`는 정리하지 않아**, 삭제된 application을 참조하던 자식 레코드가 고아(orphan)로 남는다 — `deleteApplication`(사용자 단건 삭제, cascade 있음)과 달리 이 벌크 삭제는 cascade가 없다는 점이 특히 위험하다.
3. **`clearTable`(seed.js:23-31), `clearSamsungEligibleAll`(sync.js:431-440)**: `.take(500)` 상한으로 인해 500건 초과 테이블은 **호출 1회로 완전히 비워지지 않으며**, 반환값(`deletedCount`)만 보고 "초기화 완료"로 오인할 위험이 있다(호출부에서 반복 호출 로직이 있는지는 **확인 필요**).
4. **`resetSamsungCareLedger`**(sync.js:1349-1387): `deletedApps`/`deletedAssigns`/`deletedClaims`/`deletedPayouts` 변수를 선언하지 않고 반환문(sync.js:1380-1383)에서 참조 — **호출 시 `ReferenceError`로 mutation이 실패한다.** 단, `samsungSheets` 삭제(1356-1361)와 `systemSettings` patch(1365-1375)는 이 에러 발생 이전에 이미 실행·커밋되므로, **호출자 입장에서는 실패로 보이지만 실제로는 절반의 삭제가 이미 반영된 상태**가 된다 — 매우 위험한 "부분 실패" 패턴.
5. **비인증 대량 upsert**: `saveApplicationsChunk` 등(sync.js:734-882)이 `clearCompany` 파라미터를 받아 **원수사 이름 문자열 포함 여부(`c.includes("현대")`/`c.includes("삼성")`)만으로 대량 삭제 대상을 결정**한다(sync.js:747-758 등). 이 필드에 오타나 다른 보험사명이 섞여 있으면 삭제 대상 판정이 부정확해질 수 있다.
6. **`admins`/`adminSessions` 관련 조회가 전부 전체 스캔**(17-19장): 관리자 수 자체는 적어 현재는 위험도가 낮지만, `loginAdmin`이 매 로그인 시도마다 `admins` 테이블 전체를 로드하는 구조는 관리자 수가 늘어나면 로그인 지연으로 이어질 수 있다.

## 19. DB 성능상 의심되는 부분

1. **인덱스 미사용이 구조적**: 8장에서 확인했듯 정의된 인덱스조차 절반 가까운 함수에서 사용되지 않고 `.filter()` 전체 스캔으로 대체되어 있다. 특히 시스템의 핵심 테이블인 `applications`/`assignments`/`claims`/`payouts`는 **인덱스 자체가 정의되어 있지 않아** 매 upsert마다 전체 스캔이 불가피하다. 현재 규모(수백 건, 6장 실측)에서는 체감 지연이 적을 수 있으나, 데이터가 수천~수만 건으로 늘어나면 저장 작업(특히 엑셀 재적재 시의 청크 upsert, 17장)의 소요 시간이 선형 이상으로 증가할 것으로 예상된다.
2. **`bundleAll`의 전량 로딩**(sync.js:6-105): 로그인된 모든 사용자가 화면을 열 때마다 `applications`(전체, `order("desc")`), `assignments`, `claims`, `payouts` 등 **핵심 테이블 전체를 무제한 `.collect()`** 한다(samsungEligible만 `take(100)`으로 제한, sync.js:78). 페이지네이션이 전혀 없어, 데이터가 증가할수록 최초 로딩 페이로드와 지연이 비례해 커진다.
3. **`.collect()`의 광범위한 사용**(66회, 3장): Convex 자체 가이드라인이 대규모 컬렉션에 `.collect()`를 지양하고 `@convex-dev/aggregate` 같은 전용 컴포넌트나 페이지네이션을 쓰라고 명시함에도(guidelines.md:333), 이 프로젝트는 거의 전 함수가 `.collect()`로 테이블 전체를 메모리에 올린다.
4. **로컬 JSON 파일의 전체 재작성**: `hub_apps_real.json`(실측 1.49MB)에 대한 쓰기가 발생할 때마다 파일 전체를 다시 읽고/파싱하고/직렬화해 다시 쓰는 구조로 추정된다(server.js:918-988 근거, 부분 patch가 아닌 전체 객체 조작 후 재저장 패턴) — 파일이 커질수록 매 쓰기 요청의 I/O 비용이 비례해 증가한다.
5. **이중 저장소로 인한 배가된 쓰기 비용**: 거의 모든 쓰기 작업이 "로컬 JSON 파일 쓰기 + Convex 쓰기"를 모두 수행하므로(10장), 동일 논리적 쓰기 1건이 실제로는 최소 2개의 I/O 작업(및 1~2회의 전체 테이블 스캔)을 유발한다.
6. **`getElapsedBusinessHours`/`calculateCareSettlementSchedule`류의 클라이언트 계산**(app.js:1972, 20373)은 DB 쿼리는 아니지만, `bundleAll`로 받은 전체 데이터셋을 브라우저 메모리에서 매번 재계산하는 구조라 — 서버/DB 측 집계·캐시 없이 클라이언트가 반복 계산을 떠안는 아키텍처적 부담으로 볼 수 있다(추론).

## 20. 데이터 삭제 영향 분석 (Cascade Effect / 고아 데이터 분석)

사용자 요청에 따라 "이 데이터가 삭제되었을 때 어떤 데이터가 영향을 받는가"를 코드 기준으로 정리한다.

### 20.1 `applications` 삭제

| 삭제 경로 | Cascade 여부 | 영향받는 데이터 |
|---|---|---|
| `deleteApplication({appId})` — sync.js:140-174 | **있음 (실제 코드 확인)** | 동일 `applyId`를 가진 `assignments`/`claims`/`payouts`가 함께 삭제됨(sync.js:154-170) |
| `applications.js:remove({id})` — applications.js:35-41 | **없음 (실제 코드 확인)** | Convex Document ID로 단건만 삭제, 연관 `assignments`/`claims`/`payouts`는 **그대로 남아 고아가 됨**. 단, 이 함수는 app.js 등 어디에서도 호출되지 않는 것으로 확인되어(grep 0건) 현재는 **죽은 코드로 실사용 위험은 낮음** |
| `purgeStaleApplicationsNotInList({validIds})` — sync.js:970-988 | **없음 (실제 코드 확인)** | `validIds`에 없는 application이 대량 삭제되지만 연관 `assignments`/`claims`/`payouts`는 정리되지 않아 **고아 데이터가 실제로 발생할 수 있는 현재 사용 중인 경로** |
| `resetAndPurgeLaunchData`/`purgeMockData` — sync.js:884-927, 1260-1346 | **부분적으로 있음** | 이 함수들은 `applications`뿐 아니라 `assignments`/`claims`/`payouts`를 각각 독립적으로 전체(또는 조건부) 삭제하므로 결과적으로 함께 비워지나, "동일 applyId 기준 정합성"을 보는 것이 아니라 **각 테이블을 개별적으로 통째로 비우는 방식**이라 로직상 우연히 일치할 뿐 FK 기반 cascade는 아님 |
| 로컬 `hub_apps_real.json`에서 application 삭제 | **확인 필요** | `server.js`에서 application을 개별 삭제하는 라우트 자체가 **미발견**(POST `/api/hub/real-data`는 전체 배열을 통째로 교체하는 방식, server.js:832-908) — 로컬 파일에서의 단건 cascade 삭제 로직은 존재하지 않는 것으로 보임 |

### 20.2 `admins` 삭제 — **가장 중요한 발견**

`deleteAdminDoc({adminId, username})`(sync.js:1232-1253)로 관리자 계정을 삭제해도, **해당 관리자가 이미 발급받은 `adminSessions`의 세션 토큰은 전혀 정리되지 않는다.**

- `adminSessions` 테이블은 `by_adminId` 인덱스까지 정의되어 있지만(schema.js:65), 이를 사용해 관리자 삭제 시 세션을 cascade 삭제하는 코드는 **sync.js 전체에서 미발견**.
- `verifyAdminSession`(sync.js:1106-1149)의 검증 로직을 보면: 세션 토큰 자체의 만료시각(`expiresAt`)만 확인하고, 연결된 `admin` 문서가 존재하는지는 **선택적으로만** 확인한다 — `const admin = ...find...`가 `undefined`(삭제되어 못 찾음)이면 `if (admin && admin.status==="비활성")` 조건이 자동으로 거짓이 되어 **비활성 체크를 그냥 건너뛰고 `valid: true`를 반환**한다(sync.js:1128-1147).
- **결론**: 관리자 계정을 삭제해도, 그 관리자가 로그인 시 발급받은 세션 토큰(만료까지 24시간, sync.js:1070)은 **삭제 시점부터 최대 24시간 동안 계속 유효한 인증 수단으로 남는다.** 이는 계정 삭제/권한 회수가 즉시 반영되지 않는 보안 결함이다.

### 20.3 `caregivers`/`partners`(centers)/`adjusters` 삭제

- `deleteCaregiver`(sync.js:1461-1476), `savePartner`류, `saveAdjuster`류에 대응하는 삭제 함수 모두 **해당 테이블 자체의 레코드만 삭제**하며, 이들을 이름으로 참조하는 `assignments.caregiverName`/`centerName`, `applications.adjusterName` 등은 **전혀 갱신되지 않는다**(코드 전체에서 참조 무결성 정리 로직 미발견).
- 영향: 간병인/센터/손사를 디렉토리에서 삭제해도 과거 배정/청구 기록에는 이름 문자열이 그대로 남아 "화면에는 보이지만 실제로는 삭제된 대상을 가리키는" 참조가 발생한다 — 다만 이는 원래 정본(claims/payouts 등)의 이력 보존 관점에서는 오히려 의도된 동작일 수도 있다(추론, 정확한 설계 의도는 확인 필요).

### 20.4 `samsungSheets` 삭제 (`resetSamsungCareLedger`)

- 18장 4번 항목과 동일 — `resetSamsungCareLedger`(sync.js:1349-1387) 호출 시 `samsungSheets` 전체 삭제와 `systemSettings`의 `LIVON_LAUNCH_CONFIG.samsung` 값 초기화는 **실제로 커밋**되지만, 함수 자체는 이후 `ReferenceError`로 실패 응답을 반환한다. 호출자(app.js:33641 부근, 02번 문서 참조)가 "실패"로 인식해 재시도하면, 이미 비워진 `samsungSheets`에 대해 **의도와 다른 후속 동작**을 유발할 가능성이 있다(확인 필요: 실제 재시도 로직 존재 여부).
- `applications`/`assignments`/`claims`/`payouts`에 등록된 삼성화재 고객 데이터는 이 함수의 삭제 대상에서 명시적으로 제외되어 있다(주석 "🛡️ 통합허브에 등록된 삼성화재 고객은... 100% 안전하게 보존", sync.js:1363) — **실제 코드 확인**.

### 20.5 로컬 JSON 파일 삭제/초기화의 영향

- `POST /api/admin/reset-local-data`(server.js:916-937)는 `hub_apps_real.json`을 빈 스켈레톤으로 재작성한다 — 이는 Convex와 독립적이므로, **Convex 데이터는 남아있는데 로컬 파일만 비워진 상태**가 일시적으로 발생할 수 있다(10장 트랜잭션 경계 참조). 다음 `loadConvexData()` 호출(app.js:1416) 시 Convex가 살아있다면 화면은 정상 복구되지만, 그 사이 로컬 파일에만 의존하는 경로(`server.js:802` 캐시 등)는 빈 데이터를 반환한다.

1. `convex/applications.js`의 4개 함수(`list`/`create`/`update`/`remove`)가 코드베이스 어디에서도 호출되지 않는 이유 — 완전한 죽은 코드인지, 다른 저장소(예: 별도 관리자 도구)에서 사용 중인지
2. `partners`(Convex 테이블명) ↔ `centers`(로컬 파일 키) 명명 불일치가 의도된 것인지, 리팩터링 잔재인지
3. `seedBatch`/`clearTable`(seed.js)이 실제 운영 중 호출되는 진입점이 있는지, 아니면 개발 전용 도구인지
4. `resetSamsungCareLedger`의 `ReferenceError` 버그가 실제 운영 환경에서 이미 발생한 적이 있는지(로그/장애 이력 확인 필요)
5. `hub_apps_real.json` 쓰기 시 실제로 파일 전체를 재작성하는지, 부분 갱신이 가능한 구조인지 — server.js의 캐시/쓰기 헬퍼(`server.js:200-230` 부근) 상세 코드 재검토 필요

> 이 문서에서 식별된 위험 요소(18~20장)의 우선순위화 및 구체적 개선 방안은 후속 기술부채 문서에서 다룰 예정이다.
